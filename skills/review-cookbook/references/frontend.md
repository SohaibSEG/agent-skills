# Frontend review actions

Review the interface as a complete task a person must finish. Apply the consuming project's design system, supported browsers, accessibility target, and evidence requirements. This is review-only: inspect, run authorized safe validation, and recommend corrections without editing source, tests, fixtures, or snapshots. The numbered actions operationalize the linked sources; the sources do not prescribe this cookbook's approval policy. Record untested states explicitly.

Apply only the checks relevant to the current gate. During implementation review, inspect code and state contracts; defer journey, visual and interaction review until the UX gate. Within that gate, use [User-story and journey review](user-journey.md) before component conformance checks when the task itself changes. Reading this reference does not authorize progression past a blocked gate.

## Establish the comparison

1. **Inventory applicable patterns before judging the change.** Find existing screens for the same interaction and their components, tokens, layouts, and form conventions. Map changed controls to established counterparts. Verify each counterpart serves the same purpose; superficial resemblance does not establish authority. Consistency should preserve familiar meanings and behavior. [NNGroup: usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)

2. **Compare rendered interfaces, not just component names.** Use matching data, viewport, theme, and interaction state to compare the changed screen with the applicable pattern. Examine spacing, typography, density, alignment, action placement, labels, icons, and state styling. A demonstrated inconsistency against an established applicable pattern is a blocker under this cookbook even when the feature functions. Cite the reference screen and exact discrepancy; check for an approved intentional exception. Personal taste or an unsupported redesign preference is not a finding.

3. **Walk the complete user journey.** Start at the normal entry point, find the action, inspect context, edit, encounter validation, recover, save, and revisit the result. Include cancellation, back navigation, and refresh where relevant. Record lost context or unclear completion. A working isolated component is insufficient evidence for the surrounding journey. [NNGroup: usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)

## Inspect information and state

4. **Check the information hierarchy against the task.** Identify the main question the screen answers and its primary action. Confirm routine controls remain discoverable while uncommon detail can be revealed with a clearly labeled control. Do not hide prerequisites, required errors, or decisions needed for the primary task. Reject extra disclosure levels only when they create a demonstrated navigation burden, not because every screen must be short. [NNGroup: progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/)

5. **Identify unnecessary memory demands.** Check whether labels, selected values, units, current filters, and relevant record identity remain visible at the moment of decision. Test two records with similar names. Prefer meaningful identifying context over requiring a person to remember an internal identifier from another screen. Verify that icons and abbreviated labels are understandable in context; do not assume a tooltip solves discovery on touch devices. [NNGroup: recognition and recall](https://www.nngroup.com/articles/recognition-and-recall/)

6. **Build and exercise a state matrix.** Cover view, edit, dirty, submitting, saved, empty, loading, validation failure, request failure, and permission denial when applicable. Ensure view mode is distinguishable from editable fields; cancellation restores the intended values; server refresh does not silently erase edits. Verify repeated submissions and stale responses cannot show the wrong result. Separate an empty dataset from a failed request. Check that page, section, and field feedback have an intelligible priority rather than competing banners and spinners.

7. **Verify recovery is explicit.** Submit missing, malformed, and conflicting input. Check that errors identify the affected input and describe the problem in text. Preserve valid entries so recovery does not require retyping. Ensure the person can reach the error and retry or cancel; associate messages with controls using the project's accessible form pattern. Do not claim that WCAG mandates one particular inline or summary layout. [W3C: Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)

## Inspect implementation and realistic constraints

8. **Trace CSS conflicts to the winning rule.** Inspect computed styles for problematic elements in default, hover, focus, disabled, and error states. Check global selectors, inherited styles, utility ordering, component variants, specificity, and media queries. Demonstrate the actual affected state before flagging a conflict. Recommend removing the conflicting rule or using an existing variant where appropriate; do not propose another override without identifying why it wins and which other consumers it affects.

9. **Use realistic data shapes and volume.** Exercise long labels, multiline content, absent optional values, duplicate display names, many results, and the last page. Check bounded fetching, search, pagination, and stable selection across updates. Confirm truncation retains a usable way to identify the item. Resize at supported desktop and mobile widths and zoom the page; inspect overlays, sticky controls, tables, and overflow. For a WCAG reflow check, test the applicable 320 CSS pixel width and respect exceptions for content that needs two dimensions. [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## Verify access and evidence

10. **Complete the changed flow with a keyboard.** Inspect accessible names and roles, tab order, activation, dialog dismissal, and focus after closing or saving. Ensure keyboard focus remains visible; inspect CSS resets that remove indicators. Record the exact element and state that fails. Automated checks supplement this interaction review. [W3C: Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)

11. **Check feedback without relying on sight or color alone.** Verify that status messages such as save completion and result counts are exposed to assistive technology without unnecessarily moving focus. Distinguish these messages from general content updates. Check that errors, selection, and status are distinguishable through text, shape, or another visual cue as appropriate. [W3C: Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [W3C: Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

12. **Report a reproducible correction.** Include the state, steps, expected pattern or requirement, actual result, and supporting visual evidence. For a refactor, name the existing component or boundary to reuse, what responsibility moves, and what behavior must remain unchanged. Inspect affected consumers and capture only the visual evidence permitted and required by the review scope. A screenshot demonstrates appearance; it does not prove persistence, keyboard behavior, or the complete task succeeded.
