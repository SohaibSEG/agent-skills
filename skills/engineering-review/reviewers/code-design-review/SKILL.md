# Code Design Review

Read the [shared review contract](../../references/review-contract.md) once. Inherit the parent’s frozen target, assigned gate and evidence scope.

Use at the implementation gate for responsibility, interface, coupling, control-flow and resource-lifetime questions.

Use the review procedure below. Consult the specific [Refactoring pattern](../../references/refactoring-patterns.md) only after identifying a supported correction; preserve its behavior constraints. Backend policy and frontend behavior remain with their specialist roles.

For concrete responsibility contrasts, use [wrong abstraction](../../references/worked-examples.md#wrong-abstraction) or [query with hidden effects](../../references/worked-examples.md#query-with-hidden-effects).

Return the failing caller/contract, causal code path and smallest responsibility change. Distinguish a behavior-preserving refactor from a bug fix. Reopen design when the problem is the model, not its implementation.

Use for module responsibilities, contracts, control flow, reuse and actual extension pressure. The [backend](../backend-data-security-review/SKILL.md), [frontend engineering](../frontend-engineering-review/SKILL.md) and [test-quality](../test-quality-review/SKILL.md) guides own their behavioral checks; consult only the relevant section when a seam needs it.

The procedures below are original review applications of the cited principles. They are not a mandatory architecture, a scoring checklist, or a requirement to use a named pattern.

## 1. Establish responsibility, ownership, and module depth

1. **Map the operation before judging its shape.** Identify the entry point, policy decisions, state owner, external effects, and result consumers. For each changed module, describe the responsibility in one concrete sentence and locate its public interface. Read enough surrounding code to distinguish a new defect from an existing limitation. A file containing several functions is not evidence that it has several unrelated responsibilities.
2. **Inspect what callers must know.** A useful module hides implementation decisions behind a comprehensible contract. Trace whether callers must coordinate internal steps, understand storage representation, repeat normalization, or supply implementation-specific switches. Recommend a deeper boundary when it removes that knowledge; show the particular caller obligation it would absorb. More wrappers and interfaces can increase the knowledge required. [Ousterhout: Designing Abstractions](https://web.stanford.edu/~ouster/CS349W/lectures/abstraction.html)
3. **Find competing owners of the same decision.** Search for other implementations of the changed rule, including workers, imports, UI checks, and administrative operations. Compare their inputs and intended semantics. Two independently changing copies of authorization policy can be a defect; a client hint plus authoritative server validation can be intentional. State which path diverges and under what input before recommending consolidation.
4. **Inspect dependency direction and coupling.** Follow imports, callbacks, shared mutable state, and transitive dependencies. Check whether policy now requires transport objects, provider SDK types, or another feature's private state. Identify the consequence: a supported caller cannot invoke the operation, one feature bypasses another's invariant, or a dependency cycle prevents initialization. Match any claimed layering violation to the repository's actual rule. Direct imports and a small explicit dependency can be preferable to an invented adapter hierarchy.

## 2. Make contracts and permitted states explicit

1. **Read the interface from each caller's position.** Enumerate required inputs, defaults, units, scope, ordering, ownership of mutable values, effects, result variants, and expected errors. Inspect implementation and documentation for agreement. Follow ambiguous names such as `save`, `valid`, or `amount` to their actual use; report a naming problem as blocking only when it causes a demonstrated contract error or violates an applicable authoritative rule.
2. **Construct a concrete invalid state.** Inspect optional fields, boolean combinations, loosely typed dictionaries, unchecked casts, and interchangeable identifiers. Name a representable combination the operation mishandles, and trace how it reaches production code. Recommend a discriminated state, constrained value, explicit validation, or narrower input only when it prevents that failure. Types cannot replace runtime validation of untrusted input; a new wrapper that accepts the same bad values adds no protection.
3. **Check substitution and information loss.** Compare implementations of an interface for accepted inputs, result meaning, effects, and failures. Trace deserialization, defaults, coercion, and serialization for lost distinctions such as absent versus empty, unknown versus false, or failed versus zero results. Show the consuming branch that behaves incorrectly. An interface with one implementation is neither automatically useful nor automatically unnecessary.
4. **Expose dependencies that determine behavior.** Trace clocks, randomness, current actor, configuration, global caches, and implicit sessions. Determine whether an operation receives the intended context throughout its lifetime. Recommend an explicit dependency when ambient state causes a concrete cross-request, retry, background-execution, or verification problem. Avoid replacing visible parameters with an unrestricted context bag merely to shorten the signature.

## 3. Follow data, control, effects, and resource lifetimes

1. **Trace one success path and its relevant exits.** Mark input interpretation, decisions, state changes, and external effects. Check branch priority, repeated calculations, reassignment, and duplicated predicates. For nested logic, demonstrate a missed case or explain the specific reasoning burden as advisory; nesting depth alone does not establish a defect. A shorter expression that obscures precedence or evaluation order is not necessarily an improvement.
2. **Locate every source of truth and alias.** Follow derived state, caches, copied records, mutable collections, and returned references to all their writers. Identify a transition that leaves inconsistent values or lets a caller bypass an invariant. Distinguish intentional snapshots from values expected to remain live. Recommend one owner or an explicit synchronization contract only after checking the required semantics and cost.
3. **Audit effects and error meaning together.** Inspect functions whose names suggest observation but which write, notify, acknowledge, or initialize external state. Follow exceptions and result variants through callers; look for swallowed failures, lost causes, success-shaped defaults, and retries after partial effects. Recommend an explicit operation or error contract that preserves necessary information. Do not demand exceptions over result types, or purity where an atomic read-and-change operation is the contract.
4. **Identify who acquires, transfers, and releases resources.** Trace files, sockets, transactions, locks, subscriptions, timers, and background tasks across early returns, exceptions, cancellation, and retries. Show the path that leaks, closes too early, releases twice, or outlives its valid context. When suggesting extraction or asynchronous work, check that cleanup and ownership still occur at the correct boundary; moving code can change lifetime even when its statements are unchanged.

## 4. Judge reuse, frontend seams, and extension pressure

1. **Compare reasons to change before merging similar code.** Inspect actual consumers and their policy differences. Shared code accumulating caller-specific switches may combine unrelated responsibilities; separating those policies can be clearer than expanding the abstraction. Conversely, duplicated authoritative rules can drift. Recommend sharing the common mechanism only after identifying its stable meaning, not just matching syntax. [Sandi Metz: The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)
2. **Trace frontend responsibilities separately.** Locate page composition, rendering controls, state/query hooks, API transport and decoding, and validation. Follow a real state change across them. Check whether duplicated remote and local state can disagree, a stale response can update the wrong record, or a shared component silently embeds one feature's permissions. Recommend a seam that owns the failing responsibility; extracting a hook that merely hides the same tangled effects does not resolve it. Use [UI/UX review](../ui-ux-review/SKILL.md) for interaction and visual proof.
3. **Inspect existing consumers before recommending reuse.** Compare proposed props, events, accessibility behavior, loading/error semantics, and data ownership with an established component or hook. A generic shared control should not acquire feature-specific API calls or policy solely to serve one screen. Preserve intentional differences. Require a consumer-specific regression example for a blocker; a different component decomposition is otherwise advisory.
4. **Ground extensibility in actual change pressure.** Use the current requested variant, an existing supported caller, an accepted requirement, or relevant change history. Trace which locations must change together and what breaks if one is missed. A new variant handled in serialization but omitted from an existing dispatch path is concrete evidence; hypothetical future providers are not. Compare a local branch, a coherent domain operation, and an extension mechanism against that evidence before prescribing one. Google's review guidance specifically cautions against speculative generalization. [Google: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

## Recommend the responsibility change

State what moves or becomes explicit, which owner should hold it, affected callers, and the behavior to preserve. Consult the applicable [refactoring pattern](../../references/refactoring-patterns.md) after establishing the defect. A refactor preserves observable behavior; describe intentional fixes, error changes or API changes separately. [Fowler: Definition of Refactoring](https://martinfowler.com/bliki/DefinitionOfRefactoring.html)

Use the shared contract for blocker versus preference decisions, including authoritative repository rules. Naming a principle is not a finding; [Google's review standard](https://google.github.io/eng-practices/review/reviewer/standard.html) informs this distinction. [Test quality](../test-quality-review/SKILL.md) owns proof assessment at the corrected boundary.
